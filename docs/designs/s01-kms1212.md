# S01 TCP 서버 + PING — kms1212

브랜치: [kms/s01-ping](https://github.com/kang1027/redis-clone/tree/kms/s01-ping) · [구현](https://github.com/kang1027/redis-clone/blob/kms/s01-ping/src/main.rs)

`PING`, `PING <msg>`까지. ECHO·범용 파서·인라인 명령·파이프라이닝 검증·상세 에러 문구는 다음으로 남겼다.
기준: [PING](https://redis.io/docs/latest/commands/ping/), [RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/).

## 선택

| 선택 | 이유 | 안 고른 것 / 이유 | 다시 볼 때 |
| --- | --- | --- | --- |
| Tokio 단일 스레드, 연결별 async | I/O 대기 처리, 단순한 실행 흐름 | 연결별 스레드·멀티스레드: 지금은 비용만 늘어남 | CPU 병목, S07 |
| `BufReader` + `read_exact` | 분할 입력과 바이너리 보존 | 직접 버퍼 관리: S01부터 복잡해짐 | S02 |
| 연결 유지, 순차 응답 | 매번 재접속할 필요 없음 | 요청마다 종료: 클라이언트 불편 | 연결 상태 추가 시 |
| `Result<T, Error>` | 확장할 자리만 둠. `Io`, `InvalidRequest` 두 종류 | `io::Result`: 요청 오류도 I/O 오류로 담음 | S02 오류 구분 |
| 잘못된 입력은 해당 연결 종료 | 서버와 다른 연결은 유지 | 상세 에러 응답: 이번 범위 밖 | 에러 호환 작업 시 |
| 주소·입력 한도는 CLI 설정 | 코드 수정 없이 변경 | 환경변수: 값이 숨음. 설정 파일: 처리 추가 | 배포, 설정 증가 |

기본값은 `Config`에만 둔다. 입력 한도는 학습용이며 Redis 전체 크기 범위와는 다르다.
연속 PING이 처리돼도 S02 파이프라이닝까지 검증한 것은 아니다.

## AI 사용

Rust 구현에서 AI의 보조를 받았다.
추가 테스트 케이스는 AI가 구성했다. 정상 응답뿐 아니라 분할 입력·잘못된 입력·설정 경계도 임시 소켓 검사로 확인했다.
처음부터 갈림길은 먼저 물어보도록 했다. `Result<T, io::Error>` 표기 질문을 AI가 자체 타입 제안으로 오해해서 다시 설명했다.

## Rust

- `await`: I/O를 기다리는 동안 다른 태스크 실행.
- `From` + `?`: I/O 오류를 자체 Error로 변환.
- `async move`: 연결 태스크로 소켓 소유권 이동.

발표 전 확인: 위 개념과 헤더 한도를 코드로 설명할 수 있는지. 타인 문서·케이스는 아직 확인 전.

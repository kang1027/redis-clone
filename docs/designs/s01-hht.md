# S01 TCP 서버 + PING — 한호택

- 구현 브랜치: `hht/s01-ping`
- 걸린 시간: 약 3.5시간

## 1. 무엇을 만들었나

TCP 서버를 열고 클라이언트 연결을 받아 `PING`, `PING <msg>`에 응답하도록 구현했다.

## 2. 설계 선택 — 이 문서의 핵심

| 갈림길 | 고른 것 | 이유 | 버린 선택지와 그 이유 |
| --- | --- | --- | --- |
| 예) 커넥션 처리 | tokio async 태스크 | 블로킹 커맨드가 곧 들어오는데 스레드로는 못 버틸 것 같아서 | 스레드/커넥션: 코드는 더 쉬운데 S7에서 갈아엎어야 함 |
| 커넥션 처리 | 커넥션마다 개별 스레드 | S01에서는 단순한 방식을 선택하여 TCP 연결 흐름 및 PING 처리에 집중하고 싶었다. 또한 개별 스레드 방식의 한계를 느껴보아야 나중에 async의 필요성도 체감할 수 있다고 생각했다. | async까지 다루기엔 학습 목표가 분산될 것이라고 생각했다. |

**나중에 이 선택을 뒤집어야 하는 조건:**

연결 수 증가로 스레드 수, 메모리 사용량, 컨텍스트 스위칭 비용이 증가하면 이 선택을 뒤집어야 할 것 같다.

## 3. AI를 어떻게 썼나

이 항목을 대충 쓰면 발표할 게 없습니다.

- **첫 프롬프트에 뭐라고 썼나:**
S01 코드를 구현하기 전에 TCP 서버의 구조와 보편적인 연결 흐름에 대해 알려 달라고 요청했습니다. 또한 thread-per-connection 설계와 async를 사용하는 방식의 차이를 비교해 달라고 요청했다.

- **AI 제안 중 거절한 것과 이유:**
추후 스터디 진행을 고려하여 처음부터 async를 사용하는 방법도 제안 받았으나 위에서 언급한 이유로 거절했다. 알 수 없는 명령어에 대해 연결이 종료되는 문제가 있었고 AI는 이를 실제 Redis와 똑같은 에러 코드를 반환하여 테스트를 통과시킬 것을 제안하였으나 S01의 구현 범위를 벗어나는 것으로 판단하여 거절하였다.

- **AI가 틀렸던 것 / 스펙과 달랐던 것:**
처음에는 S01에 필요한 수준보다 RESP 처리 코드가 길고 복잡해졌다. 동작 자체의 오류라기보다 S01의 학습 범위를 넘어간다고 판단하여, TCP 연결 흐름과 PING 처리에 필요한 수준으로 구현 범위를 줄였다.

- **AI 없이 내가 결정한 것:**
thread-per-connection을 선택한 것과 S01 범위 내에서 머물며 핵심 기능에 집중한 것

## 4. 내가 추가한 테스트 케이스

```text
# 대소문자
ping
PiNg hello

# 잘못된 인자 개수
PING a b
PING a b c

# 멀티바이트 문자열
PING 한글
```

- **왜 이 케이스를 넣었나:**
대소문자: 구현 할 때 대소문자 구분을 없앴는데 정상 작동하는지 확인하기 위해
잘못된 인자 개수: 요구사항은 `ping` 뒤에 오는 메시지 인자는 0개 또는 1개일 때 처리하는 것이었으므로 그 이외의 경우에 대해 에러 코드를 정상적으로 반환하는지 확인하기 위해
멀티바이트 문자열: 한글처럼 UTF-8에서 한 글자가 여러 바이트인 경우에 대한 처리가 정상적으로 동작하는지 궁금했다.


- **넣었다가 깨진 것:**
`ping` 외의 명령어가 들어왔을 때에 서버가 어떻게 동작하는지 확인하기 위해 알 수 없는 명령어를 작성하였다. 그러나 경우 return Ok(())를 하는 바람에 해당 연결이 끊어져 버렸다. 실제 redis 결과는 오류 메시지를 반환하여서 차이가 존재했다.

## 5. 막혔던 곳

<!-- 컴파일 에러, borrow checker, difftest 불일치 등. 어떻게 뚫었는지까지 -->

- `read_exact()`의 반환값인 `Result`를 처리하지 않아 clippy 경고가 발생했다.
  `?`를 붙여 오류를 상위 함수로 전달하도록 수정했다.

- 필요하지 않은 `mut`를 선언해 clippy가 경고를 발생시켰다.
  `cargo clippy -- -D warnings`에서는 warning도 error처럼 처리되기 때문에 불필요한 `mut`를 제거했다.

- `NOPE`와 같은 알 수 없는 명령어를 테스트했을 때 실제 Redis는 오류를 반환하고 연결을 유지했지만,
  현재 구현은 `return Ok(())`으로 `handle_client()`를 끝내 해당 연결을 종료했다.
  S01 범위를 고려하여 unknown command 응답 구현은 제외했다.



## 6. 새로 배운 Rust 개념

<!-- 3줄 이내. 남에게 설명할 수 있는 수준으로 -->
- `read_line()`과 `read_exact()`으로 데이터를 읽으면 `BufReader`의 현재 읽기 위치가 그만큼 앞으로 이동하며, 이미 읽은 데이터는 다음 읽기에서 다시 나오지 않는다.
- `TcpStream`을 `BufReader`로 감싸면 네트워크 데이터를 줄 단위(`read_line`)나 정해진 크기(`read_exact`)로 더 편하게 읽을 수 있다.
- `return Ok(())`은 현재 `handle_client()`를 정상 종료시키므로 해당 클라이언트의 TCP 연결도 끝난다. 실제 Redis는 잘못된 명령에도 연결을 유지하고 오류 응답을 반환한다는 차이를 확인했다.

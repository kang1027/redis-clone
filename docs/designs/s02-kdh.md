# S02 RESP 파서 + ECHO — kdh

- 구현 브랜치: `kdh/s02-echo` (로컬, 푸시 안 함)
- 걸린 시간: 따로 안 쟀습니다 (10/03 구현, 10/08~09 정리·리팩터링)

## 1. 무엇을 만들었나

ECHO보다 파서가 본론입니다. TCP로 붙어 오든 잘려 오든 명령을 정확히 꺼내서, 진짜 Redis와 같은 바이트로 응답합니다.

| 항목 | 내용 |
| --- | --- |
| `ECHO <msg>` | 인자가 정확히 1개여야 합니다 (`PING`은 0~1개) |
| 파이프라이닝 | read 한 번에 들어온 완성된 명령을 전부 처리하고, 응답은 모아서 한 번에 씁니다 |
| 쪼개진 입력 | 덜 온 조각은 버퍼에 남기고 다음 read를 기다립니다 |
| 인라인 명령 | `*`로 시작하지 않으면 인라인입니다. 공백 분리 + 따옴표까지 |
| 프로토콜 에러 | Redis와 같은 문구를 보내고 연결을 끊습니다. 커맨드 에러는 연결을 유지합니다 |

- 스펙: https://redis.io/docs/latest/commands/echo/ · https://redis.io/docs/latest/develop/reference/protocol-spec/
- 정답지 Redis: 8.10.2

## 2. 설계 선택

| 갈림길 | 고른 것 | 이유 | 버린 것 |
| --- | --- | --- | --- |
| 파서 에러 타입 (토론 주제) | 직접 만든 `ProtocolError` enum | 에러 4종이 응답 문구와 1:1입니다. `ExpectedDollar(u8)`처럼 받은 바이트를 들고 다닐 수 있고, 종류를 추가하면 `match`에서 빠진 걸 컴파일러가 잡아 줍니다 | `anyhow`: 어떤 문구를 보낼지 고르려면 다운캐스트나 문자열 비교가 필요합니다 |
| 버퍼 | cursor로 위치만 옮기고 read당 `drain` 한 번 | 명령마다 `drain`하면 남은 바이트를 매번 앞으로 복사합니다 | 명령마다 `drain` (S01 방식) |
| 응답 쓰기 | 모아서 `write_all` 한 번 | 묶어 보낼 때 시스템 콜이 줄어듭니다 | 명령마다 `write_all` |
| RESP / 인라인 판별 | 첫 바이트가 `*`인가만 봄 | Redis도 이것 하나로 가릅니다 | 상태 머신 |
| 인라인 범위 | 공백 + 따옴표 | 따옴표가 없으면 공백 든 값을 못 보냅니다 | 이스케이프까지 (이월) |
| 거대한 길이 선언 | `with_capacity` 안 씀 | `*1048576` 한 줄로 메모리를 잡히지 않으려고 | `with_capacity(count)` |
| 코드 구조 | 역할별 모듈 5개 + `Connection` 메서드 | 상태가 있는 곳(소켓 + 버퍼)만 메서드로 묶었습니다. 리팩터링 전후 바이너리에 같은 입력 59개를 보내 동작이 그대로인 걸 확인했습니다 | 커맨드마다 trait: S03·S07·S09마다 시그니처가 바뀝니다 |

**뒤집을 조건**
- S03: 커맨드가 6개가 되면 `enum Command` + `execute`로 갑니다. 무엇을 받을지는 동시성 모델이 정합니다
- S07 `BLPOP`: "꺼낼 수 있는 만큼 처리하고 한 번에 쓰기" loop가 그 명령에서 멈춰야 합니다
- S09 `MULTI`: `+QUEUED` 응답 순서를 확인해야 합니다

## 3. AI를 어떻게 썼나

- **첫 프롬프트:** "S02 관련해서 좀 조사해보셈 어케하까". AI가 구현 전에 진짜 Redis에 바이트를 쏴서 정답부터 뽑았습니다
- **AI가 정한 것:** 설계 선택 표의 위 6개는 AI 추천을 그대로 받았습니다. 제가 직접 고른 건 코드 구조 하나입니다
- **AI 제안 중 거절한 것:** 리팩터링 시점입니다. AI는 S02 세션 뒤 main에 PR로 하자고 했지만, 제 구현은 main에 안 올라가고 세션마다 머지하는 사람이 달라 구조는 어차피 바뀔 수 있어서 지금 제 브랜치에서 했습니다. 처음엔 "세션별 인터페이스 + 메서드 기반"을 생각했는데, 세션은 같은 코드를 계속 건드린다는 걸 듣고 역할별 분리로 바꿨습니다
- **AI가 틀린 것:**
  - "진짜 Redis도 이 순서"라고 주석까지 달아 둔 `expected '$'` 처리가 실측해 보니 세 군데 달랐습니다
  - 숫자 파싱에 `str::parse`를 그대로 써서 `*+1`, `$04`를 받아 줍니다 (Redis는 에러)
  - 미리 뽑아 두지 않은 입력은 추측으로 채웠고, 그게 틀렸습니다
- **이해하지 못한 채 넘어간 코드:** `split_inline_args`의 따옴표 상태(`Option<u8>`, match guard), `message()`가 `Vec<u8>`을 돌려주는 이유, `contains` / `is_some_and` / let-else는 아직 직접 안 읽었습니다
- **AI 없이 결정한 것:** 범위(이슈 그대로), 테스트 러너는 세션에서 같이 만들기, 로컬에서만 구현, 리팩터링 시점

## 5. 막혔던 곳

코드보다 개념에서 많이 막혔습니다.

- **cursor와 drain** — cursor를 처음 봐서 뭔지 몰랐습니다. 임시 로그를 찍어 보니 cursor가 0 → 14 → 28로 가고, `drain(..28)` 뒤에 덜 온 10바이트만 앞에 남았습니다
- **"한 번에 여러 명령을 보낸다"가 뭔지** — 특별한 문법이 아니라 응답을 안 기다리고 연달아 쓰는 것이었습니다. 서버는 일부러 묶은 건지 구분할 수 없어서, 붙어 와도 잘려 와도 항상 대비해야 합니다
- **S01은 두 번째 명령을 무시하는 줄 알았는데** — 실제로는 버퍼에 남아 다음 데이터가 올 때까지 밀렸습니다. 여러 개를 다 처리하게 만든 건 cursor가 아니라 안쪽 `loop`입니다
- **응답이 왜 따로 나가나** — PONG 두 개가 먼저, `hi`가 나중에 나가는 건 read 한 번당 write 한 번이라서입니다. 순서는 항상 요청 순서이고, 진짜 Redis도 똑같았습니다
- **expected '$' 세 군데** — 줄이 다 오기 전에 `$`를 검사했고, 에러 줄 안에 생 `\r`이 들어갔고, `0xff as char`가 2바이트가 됐습니다

## 6. 새로 배운 Rust 개념

- 값을 들고 있는 `enum`과, `match`가 빠진 종류를 잡아 주는 것
- `&buffer[cursor..]`는 복사 없이 보는 창문, `drain(..n)`은 앞 n바이트를 지우고 나머지를 당김
- `u8 as char`는 그 바이트가 아니라 그 번호의 유니코드 글자 (`0xff`가 2바이트가 됨)
- `str::parse::<i64>()`는 `+1`, `01`도 받아 줌
- `mod` / `pub` / `use crate::`, `struct` + `impl` + `&mut self`

## 8. 다른 사람 문서를 읽고

- **나와 제일 다른 지점 (한호택):** 범위를 ECHO + 파이프라이닝으로 잡고, S01의 `Broken`(문구 없이 끊기)을 유지했습니다. 버퍼와 쓰기도 명령마다 `drain` + 명령마다 `write_all`입니다. 같은 바이트로 비교해 보니 파이프라이닝과 쪼개진 입력은 둘 다 맞고, 인라인·프로토콜 에러·`*-1`에서는 한호택 서버가 연결을 끊습니다. 묶어 보내기(`redis-benchmark -P 50`)는 제 쪽이 3~4배 빨랐는데, 쓰기와 drain 방식이 둘 다 달라서 어느 쪽 효과인지는 못 나눴습니다
- **물어볼 것:**
  1. 인라인과 에러 문구를 S02 범위 밖으로 본 근거
  2. `*-1` 다음 PING에서 연결이 끊기는 게 의도인지 (Redis는 무시하고 계속 받음)
  3. 둘 다 enum을 골랐는데 이유가 같은지
- **남의 케이스로 내 서버를 돌려본 결과:** 한호택 `02-echo.txt` 5/5 통과. kms는 10/09 기준 아직 S02 문서가 없습니다

## 9. 알려진 차이와 한계

- 따옴표 안 이스케이프를 지원하지 않습니다. `ECHO "a\"b"`를 `unbalanced quotes`로 보고 연결을 끊습니다
- 숫자 파싱이 관대합니다. `*+1`, `*01`, `*-0`, `$+4`, `$04`를 받아 줍니다 (S02 파서, 고칠지 세션에서 결정)
- 인라인에서 `\f`를 구분자로 봅니다
- S01 코드: 커맨드 이름에 CRLF가 들면 에러 응답이 두 줄로 쪼개집니다 (가장 위험). `\xff`가 U+FFFD로 바뀌고, 128바이트 자르기가 없습니다
- 인라인 64KB 제한이 없습니다 (Redis는 `too big inline request`)

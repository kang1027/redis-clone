## 1. 무엇을 만들었나

`ECHO`와 파이프라이닝, 인라인 명령, 프로토콜 에러 문구까지 진짜 Redis와 같은 바이트로 응답합니다.

| 항목 | 내용 |
| --- | --- |
| `ECHO <msg>` | 인자가 **정확히 하나**여야 합니다 (`PING`은 0~1개라 다릅니다) |
| 파이프라이닝 | 버퍼에 쌓인 명령을 모두 꺼내 처리하고, 응답을 **한 번에** 보냅니다 |
| 인라인 명령 | `*`로 시작하지 않으면 전부 인라인. 공백 분리 + 따옴표(`"..."`, `'...'`)까지 |
| 프로토콜 에러 | 문구를 보낸 **뒤 연결을 끊습니다.** 커맨드 에러(`unknown command` 등)는 연결을 유지합니다 |

- 스펙: https://redis.io/docs/latest/commands/echo/
- RESP: https://redis.io/docs/latest/develop/reference/protocol-spec/
- 정답지 Redis: **8.10.2** (CI와 같은 버전)

## 2. 설계 선택 — 이 문서의 핵심

> ⚠️ 아래 선택은 **AI가 추천한 것을 그대로 받아들인 것**입니다. 본인이 비교해서 고른 게 아닙니다.
> 발표에서 "왜?"라는 질문을 받으면 이 표의 '이유' 칸을 **본인 말로 다시 설명할 수 있는지** 먼저 확인하세요.
> 설명이 안 되는 줄은 세션에서 뒤집을 후보입니다.

| 갈림길 | 고른 것 | 이유 | 버린 선택지와 그 이유 |
| --- | --- | --- | --- |
| 파서 에러 타입 (이슈 #2가 지정한 토론 주제) | **직접 만든 `enum`** (`ProtocolError`) | 프로토콜 에러가 4종으로 유한하고 응답 문구와 1:1로 대응합니다. `ExpectedDollar(u8)`처럼 **받은 바이트가 문구에 들어가는** 경우도 `enum`이 값을 들고 있으면 됩니다. 의존성 0개 유지 | **`anyhow`**: 에러 종류를 타입으로 구분하지 않으니, "이 에러는 어떤 문구로 보낼까"를 꺼낼 때 다운캐스트나 별도 매핑이 필요합니다. `enum`이면 `match`에서 빠뜨린 종류를 컴파일러가 잡아주는데 그 이점도 잃습니다. **`thiserror`**: 문구가 4개뿐이라 매크로 의존성이 과합니다 |
| 버퍼 관리 | **커서 인덱스**. 이번 `read`에서 처리한 만큼 모아서 **한 번만** `drain` | 명령마다 `drain`하면 파이프라인 100개에 남은 바이트를 앞으로 당기는 일이 100번입니다 | **명령마다 `drain`**: S01 방식. 코드는 더 단순하지만 파이프라인에서 낭비. **`bytes::BytesMut`**: 의존성이 늘고, 슬라이스 인덱스를 직접 다루는 학습이 사라집니다 |
| 응답 쓰기 | 처리한 명령의 응답을 **모아서 한 번에** `write_all` | 파이프라이닝의 목적이 왕복을 줄이는 것인데, 응답을 명령마다 쓰면 효과가 반감됩니다 | **명령마다 `write_all`**: 코드는 같은 길이. 다만 시스템 콜이 N번 |
| RESP / 인라인 판별 | **첫 바이트가 `*`인가**만 봅니다 | 진짜 Redis도 이것 하나로 가릅니다. 그래서 `$3\r\nabc\r\n`이 프로토콜 에러가 아니라 `unknown command '$3'` + `unknown command 'abc'` 두 개가 됩니다 (실측) | **상태 머신**: S02에는 과합니다 |
| 인라인 범위 | **공백 분리 + 따옴표**까지 | 따옴표가 인라인의 존재 이유입니다. 없으면 공백 든 값을 못 보내는 반쪽 파서이고, `unbalanced quotes`라는 에러 종류도 만들 수 없습니다 | **공백만**: 에러 1종이 사라짐. **이스케이프까지(`\x41`, `\n`)**: 문자 변환 표 작업이라 프로토콜 이해와 무관 → 아래 9번으로 넘김 |
| 거대한 선언 길이 | `Vec::new()`로 시작, **`with_capacity` 안 씀** (S01 계승) | `*1048576\r\n`은 에러가 아니라 그냥 기다립니다. 선언을 믿고 미리 잡으면 헤더 한 줄로 메모리를 잡힙니다 | **`with_capacity(count)`**: 재할당은 줄지만 악의적 입력에 약함 |
| 코드 구조 (10/09, **본인이 고름**) | **역할별 파일 분리 + 상태가 있는 곳만 구조체/메서드** — `main` / `connection` / `resp` / `reply` / `command`, 메서드는 `Connection`에만 | 590줄짜리 한 파일은 S03에서 저장소가 들어오면 찾기 힘들어집니다. 지금 상태를 들고 있는 건 커넥션 하나(소켓 + 버퍼)뿐이라 메서드는 거기에만 둡니다. 동작 변화는 없습니다 (리팩터링 전/후 바이너리에 59개 입력을 쏴서 바이트 비교) | **한 파일 유지**: 지금 비용은 0이지만 S03부터 1000줄 근처. **`enum Command` + `execute` 메서드**: `execute`가 뭘 받을지(저장소? 연결 상태?)는 S03 동시성 모델이 정하므로 지금 정하면 추측 → S03으로 미룸. **커맨드마다 trait + `Box<dyn Command>`**: 커맨드 목록이 로드맵으로 정해진 닫힌 집합이라 `enum` + `match`가 맞고, S03·S07·S09마다 trait 시그니처가 바뀌어 구현체를 전부 고쳐야 함. `match` 누락 검사도 잃음 |

코드 구조를 **지금 내 브랜치에서** 바꾼 이유(본인 판단): 이 구현은 main에 안 올라가는 내 구현입니다. 세션마다 머지하는 사람이 달라서 구조는 어차피 매번 바뀔 수 있고, 목표는 Redis 클론을 배우는 것이지 한 사람 레포를 끝까지 끌고 가는 게 아닙니다.

진짜 Redis가 정해둔 것(고른 게 아님):
- `*0`, `*-1`은 **에러가 아니고 응답도 없음**, 연결 유지
- 프로토콜 에러(`expected '$', got '+'`, `invalid multibulk length`, `invalid bulk length`, `unbalanced quotes`)는 문구를 보내고 **연결을 끊음**
- 커맨드 에러(`unknown command`, `wrong number of arguments`)는 **연결 유지**. 에러를 낸 뒤에도 `PING`이 통과함을 실측

  - 인라인 길이 제한(`too big inline request`)을 처음엔 테스트 항목으로 넣으려 했으나, **같은 입력 5번에 3번 통과/2번 에러**로 갈려서 뺐습니다 (아래 9번)
  - 이 외에는 구현 **전에** 진짜 Redis 응답을 뽑아 둔 덕에 맞았습니다. 반대로 말하면, **뽑아두지 않은 입력은 AI가 추측으로 채웠고 그게 틀렸습니다**
  - **문서를 쓴 뒤(10/08) 15개를 더 찔렀더니 12개가 또 달랐습니다.** 숫자 파싱 5개와 인라인 구분자 2개는 S02 파서 책임이고, `unknown command` 문구 5개는 S01 코드입니다 (9번). 숫자 파싱은 **Rust `str::parse::<i64>()`가 `+1` `01` `-0`을 받아준다**는 걸 모르고 그대로 쓴 결과입니다. Redis는 셋 다 프로토콜 에러입니다
- **이해하지 못한 채 넘어간 코드:** (본인이 채움) — 아래를 코드에서 직접 읽고, 설명할 수 있으면 체크. 체크 못 한 줄이 이 항목의 답입니다
  - [ ] `split_inline_args`의 따옴표 상태 처리 — `quote: Option<u8>`의 `None`/`Some`이 각각 무슨 상태인지, `Some(open) if byte == open`의 `if`(match guard)
  - [ ] `ProtocolError::message()`가 `String`이 아니라 `Vec<u8>`을 돌려주는 이유, `\r` `\n`을 공백으로 바꾸는 `matches!`
  - [ ] `!(0..=PROTO_MAX_BULK_LEN).contains(&length)` — `length < 0 || length > MAX`와 같은 뜻인 이유
  - [ ] `.is_some_and(|next| ...)` — 닫는 따옴표 뒤가 "줄 끝"일 때 왜 에러가 아닌지
  - [ ] `let Some(...) = ... else { return ... };` (let-else) — S01 문서에서 세션 때 물어보겠다고 한 것
- **AI 없이 내가 결정한 것:** 범위 4개, 러너 보류, 로컬 전용

## 4. 내가 추가한 테스트 케이스

`tests/cases/02-echo.txt` (difftest용 — `redis-cli`를 거치므로 **항상 RESP 배열로만** 전송됩니다):

```
ECHO hello
echo hello
ECHO 123
ECHO
ECHO a b
ECHO a b c
ECHO 한글
PING
PING hello
NOPE a b
```

- **왜 이 케이스를 넣었나:**
  - `ECHO` / `ECHO a b` — PING은 `PING a b`가 에러지만 `PING hello`는 정상. **ECHO는 정확히 1개**라서 기준이 다릅니다
  - `ECHO 한글` — 응답 길이는 `$6`(바이트)이지 `$2`(글자)가 아닙니다
  - 마지막 `PING`류 3줄 — ECHO를 넣다가 S01이 깨지지 않았는지 보는 회귀 검사
- **넣었다가 깨진 것:** 구현 전에는 10개 중 7개가 빨간불이었습니다 (`ECHO`가 `unknown command`로 나옴). 이게 의도한 출발점입니다

## 5. 막혔던 곳

- **`*`가 아니면 에러일 줄 알았는데 전부 인라인이었습니다.** `$3\r\nabc\r\n`이 프로토콜 에러가 아니라 **에러 두 개**(`unknown command '$3'`, `unknown command 'abc'`)로 나왔습니다. S01의 `Some(_) => Broken` 한 줄이 S02에서 `Some(_) => parse_inline`으로 정반대가 됩니다
- **에러가 2계층이라는 걸 먼저 몰랐습니다.** 진짜 Redis에 에러를 낸 뒤 `PING`을 더 보내 보니 커맨드 에러는 연결이 살고 프로토콜 에러는 끊겼습니다. 이걸 모르고 구현했다면 오타 한 번에 연결이 끊기는 서버가 됐을 겁니다
- **`expected '$', got '+'` 에러에서 세 번 틀렸습니다.** 처음엔 "줄이 오기 전에 첫 바이트부터 보는 게 진짜 Redis 방식"이라고 가정하고 주석까지 달았는데, 실측해 보니 반대였습니다.

  | 입력 | 진짜 Redis | 처음 구현 | 원인 |
  | --- | --- | --- | --- |
  | `*1\r\n+PIN` (줄 덜 옴) | **대기** | 즉시 에러 | 줄 완성 **전에** `$`를 검사함 |
  | `*1\r\n\r\n` (빈 줄) | `got ' '` | `got '\r'` — **에러 줄 안에 생 CR이 들어가 프로토콜이 깨짐** | `\r` `\n`을 공백으로 안 바꿈 |
  | `*1\r\n\xff\r\n` | `got '\xff'` (1바이트) | `got '\xc3\xbf'` (2바이트) | `0xff as char`가 UTF-8로 인코딩됨 |

  고친 방법: `read_line`을 먼저 하고 그 뒤에 `$`를 검사 / `message()`가 `String`이 아니라 `Vec<u8>`을 돌려주고 `\r` `\n`은 공백으로 치환. 세 번째가 Rust 쪽 교훈입니다. **`u8 as char`는 "그 바이트 그대로"가 아니라 "그 번호의 유니코드 글자"입니다.** 바이트를 다루는 코드에서 `String`을 거치면 이런 일이 생깁니다
  - 이걸 raw 비교에 5개 케이스(위 3개 + `\n` 단독 + `*1\r\nX`)로 추가했습니다. **AI가 쓴 "진짜 Redis도 그렇다"는 문장은 실측하기 전엔 믿으면 안 된다**는 사례입니다
- **clippy 3건** (`-D warnings`): ① `if let` 안의 `if`를 합치라는 경고 2건 ② `length < 0 || length > MAX`를 `!(0..=MAX).contains(&length)`로 쓰라는 경고. 첫 번째는 `if !replies.is_empty()` 검사를 아예 지웠습니다 (`write_all`에 빈 슬라이스를 주면 아무것도 안 하므로)
- **difftest로는 이번 세션의 절반을 검사할 수 없었습니다.** 그래서 raw 소켓으로 따로 비교했습니다 (4번)

## 6. 새로 배운 Rust 개념

- **값을 들고 있는 `enum`** — `ExpectedDollar(u8)`처럼 변형(variant)이 데이터를 가질 수 있어서, "어떤 에러인가"와 "무엇을 받았나"가 한 타입에 들어갑니다. `match`가 모든 변형을 다루도록 컴파일러가 강제합니다
- **`#[derive(Debug, PartialEq, Eq)]`** — 이게 있어야 `assert_eq!(parse_command(...), Parsed::Incomplete)`처럼 `enum`끼리 비교하는 테스트를 쓸 수 있습니다. S01에서는 `matches!`로 우회했었습니다
- **슬라이스 `&buffer[cursor..]`** — 복사 없이 "버퍼의 이 지점부터"를 가리킵니다. 처리한 만큼 `cursor`만 올리고 `drain`은 마지막에 한 번 합니다
- **모듈과 `pub`** — 파일 하나가 모듈 하나입니다. 다른 파일의 함수를 쓰려면 그쪽에서 `pub`을 붙이고 이쪽에서 `use crate::...`로 가져옵니다. `pub`이 없는 `parse_array` 같은 함수는 같은 파일 안(그 파일의 테스트 포함)에서만 부를 수 있습니다
- **`struct` + `impl` + `&mut self`** — 함수 안 지역 변수였던 소켓과 버퍼를 `Connection`에 묶고, 메서드가 `&mut self`로 그 상태를 고칩니다

## 9. 알려진 차이와 한계

### 일부러 안 맞춘 것: 따옴표 안 이스케이프 (실측)

| 입력 (인라인) | 진짜 Redis | 우리 |
| --- | --- | --- |
| `ECHO "a\x41b"` | `aAb` (`$3`) | `a\x41b` 그대로 (`$6`) |
| `ECHO "a\nb"` | 개행이 들어간 `a`↵`b` (`$3`) | `a\nb` 그대로 (`$4`) |
| `ECHO "a\"b"` | `a"b` (`$3`) | **`unbalanced quotes` 에러 + 연결 종료** |
| `ECHO 'a\'b'` | `a'b` (`$3`) | **`unbalanced quotes` 에러 + 연결 종료** |

마지막 두 줄이 위험합니다. 단순히 "변환이 안 된다"가 아니라 **정상 입력을 에러로 보고 연결을 끊습니다.** 이스케이프를 뺀 대가가 이것입니다.

### 10/08에 새로 찾은 차이 (일부러가 아님, 아직 안 고침)

**S02 파서 — 숫자 파싱.** `parse_number`가 Rust의 `str::parse::<i64>()`를 그대로 씁니다. Rust는 앞에 붙은 `+`, 앞자리 `0`, `-0`을 숫자로 받아주는데, 진짜 Redis는 셋 다 프로토콜 에러로 보고 연결을 끊습니다.

| 입력 | 진짜 Redis | 우리 |
| --- | --- | --- |
| `*+1\r\n$4\r\nPING\r\n` | `invalid multibulk length` + 연결 종료 | `+PONG` |
| `*01\r\n$4\r\nPING\r\n` | `invalid multibulk length` + 연결 종료 | `+PONG` |
| `*-0\r\n` | `invalid multibulk length` + 연결 종료 | 응답 없음 (빈 명령으로 처리) |
| `*1\r\n$+4\r\nPING\r\n` | `invalid bulk length` + 연결 종료 | `+PONG` |
| `*1\r\n$04\r\nPING\r\n` | `invalid bulk length` + 연결 종료 | `+PONG` |

**S02 파서 — 인라인 구분자.** 우리는 `is_ascii_whitespace`로 끊는데, 이 함수는 `\f`(form feed)도 공백으로 봅니다.

| 입력 | 진짜 Redis | 우리 |
| --- | --- | --- |
| `ECHO a\x0cb\r\n` | `$3` — `a\x0cb`가 인자 하나 | `wrong number of arguments` (인자 둘로 쪼갬) |
| `ECHO a\x00b\r\n` | 0.4초 안에 응답 없음 (원인 미확인) | `$3` — `a\x00b` |

**S01 코드 — `unknown command` 문구.** S02에서 인라인이 생기면서 `nc`로도 쉽게 닿는 경로가 됐습니다.

| 입력 | 진짜 Redis | 우리 |
| --- | --- | --- |
| `*1\r\n$1\r\n\xff\r\n` (인라인 `\xff\r\n`도 같음) | `'\xff'` (1바이트) | `'\xef\xbf\xbd'` — `String::from_utf8_lossy`가 바꿈 |
| `*1\r\n$4\r\na\r\nb\r\n` (이름에 CRLF) | `'a  b'` (CR, LF가 공백 둘로) | **생 CRLF가 에러 줄 안에 들어감** |
| 200바이트짜리 이름 | 128바이트에서 자름 | 안 자름 |
| 50바이트 인자 5개 | 인자 부분을 `50 + 50 + 22`바이트에서 자름 | 안 자름 |

이름에 CRLF가 든 경우가 제일 위험합니다. 응답 한 줄이 두 줄로 쪼개지니 **클라이언트가 응답 개수를 잘못 세고, 그 뒤 응답이 전부 한 칸씩 밀립니다.** 5번의 `got '\r'`과 같은 종류의 버그가 S01 코드에 남아 있던 것입니다. `\xff` 건도 5번의 "바이트를 `String`으로 거치면 생기는 일"과 같은 교훈입니다. 자르는 길이 규칙은 실측값만 적었고 소스는 확인하지 않았습니다.

### 한계

- **인라인 길이 제한이 없습니다.** 진짜 Redis는 64KB를 넘으면 `too big inline request`로 끊습니다. 우리는 줄바꿈 없이 계속 보내는 클라이언트 하나가 **버퍼를 끝없이 키울 수 있습니다.** 테스트로 못 넣은 이유는 진짜 Redis의 이 검사가 **같은 입력에 결과가 갈리기 때문**입니다 (같은 70KB를 한 번에 5번 보내 3번 정상, 2번 에러. 반대로 40KB + 나머지로 나눠 보내면 3번 모두 정상이었습니다). 원인은 **추정**입니다: 한 번에 읽은 바이트 수에 따라 검사가 걸리는 것으로 보이는데, 소스는 확인하지 않았습니다. 하지만 테스트가 불가능한 것과 필요 없는 것은 다릅니다. **세션에서 짚을 가치가 있는 지점입니다**
- 상한을 일부만 맞췄습니다. `INT_MAX` 초과 배열 개수와 512MB 초과 벌크 길이는 맞췄지만, `*1048577`까지만 "대기"를 확인했고 그 사이 구간은 실측하지 않았습니다
- 벌크 길이 512MB까지 선언을 허용하므로, 한 커넥션이 그만큼을 버퍼링할 수 있습니다 (진짜 Redis도 같은 한도)
- 커넥션당 스레드라 이 한계들이 **스레드 수만큼 곱해집니다**

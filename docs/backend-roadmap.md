# 백엔드 관점 세션 로드맵 (S1~S10)

"Redis 명령어를 다 구현한다"가 아니라, **명령어 하나를 서버가 어떻게 처리하는지**를 배우는 순서입니다.

---

## 0. 먼저 — 백엔드는 Redis를 어디에 쓰나

### Redis는 트래픽 경로 위에 없습니다

```
클라이언트 → (LB) → 백엔드 서버 ──┬→ Redis
                                  └→ DB
```

트래픽은 항상 백엔드 서버로 먼저 들어갑니다. Redis는 DB 앞을 가로막는 프록시가 **아니라**,
백엔드가 요청을 처리하다가 필요할 때 직접 호출하는 대상입니다.
어디를 먼저 볼지, 언제 지울지는 전부 **앱 코드가 정합니다.**

```python
data = redis.get(f"product:{id}")      # 앱이 명시적으로 Redis에 물어봄
if data is None:
    data = db.query(...)                # 없으면 앱이 명시적으로 DB에 감
    redis.set(f"product:{id}", data, ex=300)
```

Redis는 DB의 존재를 모르고, DB도 Redis의 존재를 모릅니다. 둘을 잇는 건 앱 코드뿐입니다.
그래서 **상품을 수정하고 `DEL`을 빼먹으면 낡은 값이 TTL 동안 계속 나갑니다.**
실무 Redis 장애의 대부분은 서버가 고장 나서가 아니라, 앱이 넣고 지우는 규칙을 잘못 짜서 생깁니다.

### 한 줄 정의

> **Redis = 여러 백엔드 서버가 같이 쓰는 외부 메모리.**
> 거기에 DB 조회 결과를 넣으면 캐시, 작업 목록을 넣으면 큐, 표식을 넣으면 분산 락이 됩니다.

서버가 1대면 그냥 프로세스 변수로 해도 되는 걸, 여러 대라서 밖으로 빼낸 것입니다.
그래서 Redis는 **캐시 전용 도구가 아닙니다.** 아래 표의 절반은 DB와 아무 상관이 없습니다.

### 용도별 정리

| 상황 | 명령어 | 왜 DB로는 안 되나 | 세션 |
| --- | --- | --- | --- |
| **캐시** — 상품 상세, 프로필 | `GET` / `SET ... EX` | DB 50ms → Redis 0.3ms. TTL로 알아서 만료 | S3, S4 |
| **세션 저장** — 로그인 유지 | `HSET` / `HGETALL` + TTL | 서버 3대면 어디로 붙어도 세션이 보여야 함 | S4, S8 |
| **Rate limit** — "1분에 60번" | `INCR` + `EXPIRE` | 요청마다 DB INSERT 하면 rate limit이 병목이 됨 | S5 |
| **분산 락** — 크론잡 중복 실행 방지 | `SET lock v NX EX 30` | 락은 한 군데서 관리해야 함. `NX`가 "없을 때만 성공"이라 락이 됨 | S4 |
| **작업 큐** — 메일 발송, 썸네일 생성 | `LPUSH` + `BRPOP` | 워커가 DB를 1초마다 폴링하면 DB가 죽음 | S6, S7 |
| **멱등성** — 결제 요청 중복 방지 | `SET req:{id} 1 NX EX 600` | "1등만 통과"를 원자적으로 판정해야 함 | S4 |
| **카운터** — 조회수, 좋아요 | `INCR` | 인기글 하나에 초당 수천 UPDATE면 row lock 경합으로 DB가 뻗음 | S5 |
| **랭킹** — 리더보드 | `ZADD` / `ZRANGE` | `ORDER BY ... LIMIT`을 실시간으로 계속 때릴 수 없음 | 확장 |
| **실시간 알림** — 웹소켓 서버 여러 대 | `PUBLISH` / `SUBSCRIBE` | 메시지 받은 서버가 다른 서버에 붙은 유저에게도 밀어야 함 | 확장 |

### Redis를 쓰면 안 되는 경우

- **원본 데이터 저장소로 사용** — 메모리라 날아갈 수 있습니다. 날아가도 되는 것만 넣는 게 원칙입니다
- **큰 값 저장** — 싱글스레드라 1MB짜리 하나를 처리하는 동안 다른 요청이 전부 대기합니다
- **조건 검색** — `WHERE age > 30 AND city = ?` 같은 건 못 합니다. 키로 찍어 꺼내는 구조입니다

### 우리가 만드는 건 어느 쪽인가

위 표의 "왜 DB로는 안 되나"는 전부 **싱글스레드 + 원자적 실행**이라는 한 가지 성질에서 나옵니다.
우리는 그 성질을 만드는 쪽, 즉 **정책이 없는 쪽**을 구현합니다.
"언제 캐시할지"는 구현 범위에 없고, "명령어를 원자적으로 실행해 정확한 응답을 돌려주는 것"까지가 범위입니다.

## 세션 목록

각 세션은 `만들 것 / 실무에서 / 백엔드 개념 / Rust 개념 / 설계 토론 / 완료 기준`으로 되어 있습니다.
설계 토론 항목은 **구현 전에 Issue에서 결론을 내고**, 그 근거를 PR 본문에 적습니다.

### S1. TCP 서버 + `PING`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | `PING`, `PING <msg>` |
| 실무에서 | 로드밸런서와 쿠버네티스 헬스체크가 이걸 때립니다. `redis-cli ping`으로 살았는지 확인하는 그 명령어 |
| 백엔드 | accept 루프, 커넥션 하나당 무슨 일이 일어나는지, Simple String(`+PONG\r\n`) |
| Rust | `Result`와 `?`, `loop`, 소유권 첫 만남 |
| 설계 토론 | 커넥션마다 스레드 vs async 태스크 — 여기서 정한 게 S7까지 따라옵니다 |
| 완료 기준 | `redis-cli -p 6380 PING` → `PONG`, difftest 01 케이스 통과 |

### S2. RESP 파서 + `ECHO`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | `ECHO`, 명령어를 RESP Array로 제대로 파싱 |
| 실무에서 | 파이프라이닝은 실제 성능 튜닝 수단입니다. 명령어 100개를 한 번에 보내면 왕복 100번이 1번이 됩니다 |
| 백엔드 | 길이 기반 프로토콜, 패킷이 잘려 들어오는 경우, 파이프라이닝 |
| Rust | `enum` + `match`, `&[u8]` vs `Vec<u8>`, 버퍼 관리 |
| 설계 토론 | 파서 에러 타입 — 직접 만든 `enum` vs `anyhow`. 내내 고치게 되니 지금 정합니다 |
| 완료 기준 | 두 명령어를 붙여 보내면 응답도 두 개가 나옴 |

### S3. `SET` / `GET` / `DEL` / `EXISTS`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | 위 4개 + 없는 키는 Null Bulk String |
| 실무에서 | **cache-aside 패턴.** `GET` 해보고 없으면 DB 갔다가 `SET`, 원본이 바뀌면 `DEL`. 실무 Redis 코드의 대부분이 이것입니다 |
| 백엔드 | 여러 커넥션이 하나의 저장소를 공유한다는 문제. 여기가 진짜 시작점입니다 |
| Rust | `HashMap`, `Arc<Mutex<...>>`, `.clone()`이 실제로 뭘 복사하는지 |
| 설계 토론 | 동시성 모델: `Arc<Mutex<HashMap>>` / 키 해시 샤딩 / actor + 채널 |
| 완료 기준 | 커넥션 두 개로 한쪽에서 `SET`, 다른 쪽에서 `GET`이 보임 |

### S4. TTL — `EXPIRE` / `TTL` / `PERSIST` / `SET` 옵션

| 항목 | 내용 |
| --- | --- |
| 만들 것 | `EXPIRE`, `TTL`, `PERSIST`, `SET`의 `EX`/`PX`/`NX`/`XX` |
| 실무에서 | 세션 만료, 캐시 만료, **분산 락**(`SET lock v NX EX 30`), 결제 중복 방지. `NX`(없을 때만 성공) 하나로 락과 멱등성이 둘 다 됩니다. TTL을 안 걸면 메모리가 새서 언젠가 터집니다 |
| 백엔드 | **캐시 서버의 본질.** 만료된 키를 언제 지우는가 — 읽을 때(lazy) vs 주기적으로 훑기(active). 진짜 Redis는 둘 다 합니다 |
| Rust | `Instant`/`Duration`, 백그라운드 태스크, 시간을 어떻게 테스트할 것인가 |
| 설계 토론 | 만료 시각을 값 옆에 둘지 별도 테이블에 둘지 / active expiration을 이번에 할지 미룰지 |
| 완료 기준 | TTL 지난 키가 `GET`에서 안 보이고 `DBSIZE`에서도 결국 사라짐 |

### S5. `INCR` / `DECR` / `INCRBY`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | 위 3개 + 숫자가 아닐 때 정확한 에러 문구 |
| 실무에서 | **rate limiter**(`INCR` + `EXPIRE` 60), 조회수/좋아요 카운터. 인기글에 초당 수천 UPDATE를 DB로 보내면 row lock 경합으로 뻗으니, Redis에 쌓고 주기적으로 DB에 flush 합니다 |
| 백엔드 | **원자성.** 앱에서 `GET` → `+1` → `SET` 하면 왜 틀리는지(lost update), 왜 서버가 해줘야 하는지 |
| Rust | 문자열↔정수 파싱, `i64` 오버플로 처리(`checked_add`) |
| 설계 토론 | 값을 항상 문자열로 저장할지, 정수는 정수로 저장할지(진짜 Redis는 후자) |
| 완료 기준 | `SET k abc` 후 `INCR k` → `ERR value is not an integer or out of range` |

### S6. List — `LPUSH` / `RPUSH` / `LPOP` / `RPOP` / `LRANGE` / `LLEN`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | 위 6개 + 다른 타입 키에 쓰면 `WRONGTYPE` |
| 실무에서 | **작업 큐의 자료구조.** Sidekiq, Bull, Celery가 전부 Redis List 위에 올라가 있습니다. 최근 알림 N개 같은 고정 길이 목록에도 씁니다 |
| 백엔드 | 음수 인덱스, 빈 리스트가 되면 키 자체가 사라지는 규칙 |
| Rust | 값을 담는 `enum`(`Value::Str` / `Value::List`), `VecDeque` |
| 설계 토론 | `VecDeque` vs `Vec` vs 직접 만든 연결 리스트 |
| 완료 기준 | `LRANGE key 0 -1`이 진짜 Redis와 바이트 단위로 같음 |

### S7. `BLPOP` / `BRPOP` — 블로킹

| 항목 | 내용 |
| --- | --- |
| 만들 것 | `BLPOP key [key ...] timeout` (timeout 0 = 무한) |
| 실무에서 | **워커 프로세스가 일을 기다리는 방식.** 폴링(`LPOP`을 1초마다)하면 일이 없어도 계속 때려서 낭비고, 일이 생겨도 최대 1초 늦습니다. `BRPOP`이면 즉시 깨어납니다 |
| 백엔드 | **이 스터디에서 제일 값어치 있는 세션.** 응답을 당장 못 주는 클라이언트를 어떻게 재우고, `LPUSH`가 왔을 때 어떻게 깨우는가. 대기 순서(먼저 기다린 사람이 먼저)를 어떻게 보장하는가 |
| Rust | 채널, `tokio::select!`, `Notify`, 타임아웃 |
| 설계 토론 | 대기자 목록을 어디에 둘지 / S3에서 고른 동시성 모델이 여기서 버티는지 — **못 버티면 여기서 바꿉니다** |
| 완료 기준 | A가 대기 중일 때 B가 `LPUSH` 하면 A가 즉시 받음. 대기자 2명이면 먼저 온 쪽이 받음 |

### S8. Hash — `HSET` / `HGET` / `HGETALL` / `HDEL` / `HINCRBY`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | 위 5개 |
| 실무에서 | **세션 저장소.** JSON을 통째로 넣는 것과 달리 **필드 하나만 고칠 수 있습니다.** 장바구니에 상품 하나 추가할 때 전체를 다시 쓰지 않아도 됩니다 |
| 백엔드 | 부분 갱신, 값이 또 다른 자료구조인 경우의 접근 |
| Rust | 중첩 자료구조의 소유권/빌림 |
| 설계 토론 | 필드 수가 적을 때도 `HashMap`을 쓸지(진짜 Redis는 작으면 배열로 저장합니다) |
| 완료 기준 | `HGETALL` 응답의 필드 순서/형식이 진짜 Redis와 같음 |

### S9. `MULTI` / `EXEC` / `DISCARD` / `WATCH`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | 위 4개 |
| 실무에서 | 재고 차감, 포인트 차감처럼 **"내가 읽은 값이 그대로일 때만 쓴다"**가 필요한 경우. `WATCH`로 낙관적 락(CAS)을 겁니다 |
| 백엔드 | **Redis 트랜잭션은 롤백이 없다**는 사실과 그 이유. 명령어를 모아뒀다가 한 번에 실행하는 구조 |
| Rust | 커넥션마다 갖는 상태(큐잉된 명령 목록), 키 버전 추적 |
| 설계 토론 | `WATCH` 무효화를 키 버전 카운터로 할지, 감시자 목록으로 할지 |
| 완료 기준 | `WATCH k` 후 다른 커넥션이 `k`를 바꾸면 `EXEC`가 Null 반환 |

### S10. `KEYS` vs `SCAN` + `TYPE` / `DBSIZE`

| 항목 | 내용 |
| --- | --- |
| 만들 것 | `KEYS pattern`, `SCAN cursor [MATCH p] [COUNT n]`, `TYPE`, `DBSIZE` |
| 실무에서 | **프로덕션 사고 단골 1위.** 운영 중에 `KEYS *` 한 번 치면 그동안 서버 전체가 멈춥니다. 그래서 실무 규칙은 "`KEYS` 금지, `SCAN` 사용"입니다. 이유를 직접 만들어보며 이해합니다 |
| 백엔드 | 싱글스레드 서버에서 O(N) 명령이 갖는 의미, 커서 기반 순회, SCAN이 "중복은 나와도 누락은 없다"를 보장하는 방식 |
| Rust | 반복자, 글롭 패턴 매칭 직접 구현 |
| 설계 토론 | 커서를 어떻게 표현할지(해시 버킷 인덱스 vs 스냅샷) |
| 완료 기준 | 키 1만 개를 넣고 `SCAN`으로 전부 순회했을 때 누락이 없음 |

## 확장 (S1~S10을 끝낸 뒤)

| 주제 | 명령어 | 실무에서 |
| --- | --- | --- |
| Set | `SADD` `SREM` `SISMEMBER` `SCARD` | 중복 제거, 태그/권한 체크, 오늘 방문한 유저 집합 |
| Sorted Set | `ZADD` `ZRANGE` `ZRANGEBYSCORE` `ZINCRBY` | 리더보드, 슬라이딩 윈도우 rate limit, 딜레이 큐. 자료구조 난이도는 최상 |
| Pub/Sub | `SUBSCRIBE` `PUBLISH` | 웹소켓 서버가 여러 대일 때 알림 팬아웃, 캐시 무효화 전파 |
| 영속성 | `SAVE` / `BGSAVE` 또는 AOF | 재시작 후 복구. fork 대신 뭘 할지가 토론거리 |
| 관측성 | `INFO` `COMMAND` | 운영 지표, redis-cli 정상 접속 |

## 이번 스터디에서 버리는 것

- `SETBIT`/`BITCOUNT`, `PFADD`(HyperLogLog), `GEOADD` — 자료구조 트릭이지 서버 설계 학습이 아닙니다
- `EVAL`(Lua) — 인터프리터를 붙이는 순간 스터디 범위를 벗어납니다
- Cluster, ACL, `MODULE`, 복제(`REPLICAOF`/`PSYNC`) — 범위 밖. 복제는 다 끝낸 뒤 보너스
- Stream(`XADD`/`XREADGROUP`) — 백엔드 관점에선 매력적이지만 난이도가 S1~S10 전체와 맞먹습니다
